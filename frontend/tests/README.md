# Acceptance tests

В каталоге `tests/features` находятся BDD-сценарии на Gherkin для включения в программу и методику испытаний.

В каталоге `tests/acceptance` находятся исполняемые acceptance-тесты Playwright, проверяющие основные сценарии через REST API backend.

Файл `coverage-matrix.md` связывает требования раздела 4.2 ТЗ, Gherkin-сценарии и исполняемые acceptance-тесты.

## Структура сценариев

Сценарии разбиты по функциональным блокам ТЗ:

- `01-auth-and-access.feature` - аутентификация, авторизация, справочники, аудит
- `02-asset-management.feature` - управление оборудованием
- `03-software-management.feature` - управление программным обеспечением
- `04-ticket-management.feature` - управление заявками
- `05-asset-movement-acts.feature` - акты перемещения ОС-2
- `06-asset-writeoff.feature` - списание оборудования ОС-4
- `07-notifications.feature` - уведомления
- `08-employee-management.feature` - управление сотрудниками
- `09-analytics.feature` - аналитика и отчётность

## Проверяемые сценарии

- Авторизация пользователей с ролями `EMPLOYEE`, `IT_SPECIALIST`, `IT_MANAGER`, `HR`
- Разграничение доступа к операциям по ролям
- Регистрация, просмотр, редактирование и фильтрация оборудования
- Регистрация, просмотр, редактирование, установка, обновление и удаление ПО
- Создание, назначение, выполнение и закрытие заявок
- Оформление актов выдачи, возврата и списания
- Формирование PDF и XLS для актов ОС-2 и ОС-4
- Формирование уведомлений по значимым событиям
- Создание, изменение и удаление сотрудника HR-специалистом
- Получение аналитической сводки
- Проверка бизнес-ограничений и журнала аудита

## Подготовка

Перед запуском тестов должны быть запущены:

- PostgreSQL на порту `5432`
- backend AssetFlow на порту `8081`

Для проверки PDF-форм backend использует один из двух вариантов:

- LibreOffice, если он установлен на сервере и доступен по стандартному пути
- fallback-формирование PDF из HTML, если LibreOffice не найден

XLS-формы формируются без LibreOffice.

Тесты используют стандартные учётные записи, создаваемые `DevBootstrap`:

- `admin / admin` - IT-специалист
- `manager / manager` - IT-менеджер
- `user / user` - сотрудник
- `hr / hr` - HR-специалист

## Установка зависимостей

```bash
npm install
```

## Запуск

```bash
npm run test:acceptance
```

## Просмотр HTML-отчёта

```bash
npx playwright show-report
```

Если backend запущен не на `http://localhost:8081`, можно указать адрес через переменную окружения `API_BASE_URL`.

## Тестовые данные

Acceptance-тесты выполняют реальные HTTP-запросы к backend и используют подключённую PostgreSQL-базу приложения.

Во время выполнения тестов создаются:

- записи оборудования
- записи программного обеспечения
- установки ПО
- заявки
- акты ОС-2 и ОС-4
- уведомления
- записи журнала аудита
- временные сотрудники для HR-сценариев

Часть временных сотрудников удаляется в рамках теста. Исторические данные, такие как заявки, акты, уведомления и журнал аудита, не удаляются, потому что они отражают результат выполненных операций.

Для повторяемых испытаний рекомендуется использовать отдельную тестовую БД или очищать данные перед прогоном.

## Ограничения покрытия

Часть требований проверяется через API-тесты. UI-специфичные требования, например переход к парному акту в таблице и визуальная пригодность печатной формы, должны дополнительно фиксироваться в ПМИ как ручные проверки через веб-интерфейс.
